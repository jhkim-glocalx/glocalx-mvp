# GlocalX v2 — 딜리버리 계획

> **English:** [delivery-plan.md](delivery-plan.md)

상태: 제안됨
날짜: 2026-07-16
동반 문서: [README.ko.md](README.ko.md) (범위), [architecture.ko.md](architecture.ko.md) (설계)

작업 모델: Claude가 직접 구현·테스트하고(Codex는 2차 의견 리뷰어일 뿐, 예:
위험한 변경에 `/codex review`), 그다음 검증(diff 리뷰 + `/qa` + 테스트 스위트)한
뒤 GitHub Flow로 출시 — `feat/*` 브랜치를 `main`에 직접 PR하고, PR별 Vercel
프리뷰를 스테이징으로 사용(`dev` 브랜치는 `feat/social-post-publishing`으로
폐지되며, Phase 0 전에 머지되어야 함). 아래 각 단계는 소수의 리뷰 가능한 PR로
착지하도록 크기가 잡혀 있고, 각각 스텁 어댑터 경계 뒤에서 독립적으로 출시
가능합니다.

## 단계 지도

| Phase | 결과                                                 | 의존           | 예상   |
| ----- | ---------------------------------------------------- | -------------- | ------ |
| 0     | 모노레포 재구조화, 어드민 스캐폴드, 어드민 인증      | —              | 1 wk   |
| 1     | 채팅 MVP: 위젯 + 콘솔 + 맥락 텔레메트리 (휴먼 모드)  | 0              | 1.5 wk |
| 2     | AI 응답기 + AI/휴먼 모드 토글                        | 1              | 1 wk   |
| 3     | 마케팅 파이프라인: 인테이크 → 제작 → go/no-go → 게시 | 0 (1–2와 병행) | 2 wk   |
| 4     | GBP 조직-접근 온보딩 강화                            | 0              | 1 wk   |
| 5     | 스테이징 코호트 준비: 시드, 운영 문서, QA 패스       | 1–4            | 0.5 wk |

Phase 1–2(채팅)와 3(파이프라인)은 Phase 0 이후 병렬 가능한 워크스트림입니다.
총합: 현재 팀으로 ~5–6주.

타임라인은 설계상 잠정적입니다: 파일럿-매장 모집과 빌드 진행에 따라 유연하게
변합니다. 수동-서비스 트랙(Phase 0 병행 워크스트림)이 조향 신호입니다 — 거기서
나온 증거(승인 마찰, 요청량, 응답 행동)가 단일 고정 체크포인트가 아니라 지속적으로
단계 순서와 범위를 조정합니다.

## Phase 0 — 기반 (동작 변화 제로)

목표: 레포가 어드민 앱이 배포된 워크스페이스 모노레포가 되고, 오너 앱은
바이트 단위로 동일하게 동작한다.

태스크:

1. **워크스페이스 재구조화.** 기존 앱을 `apps/owner-app`으로 이동;
   `packages/db`, `packages/domain`, `packages/integrations`, `packages/ui`를
   만들고 `src/server/db`, `src/domain`, `src/integrations`, 디자인 토큰을 각각
   재배치. 경로 별칭만, 빌드 단계 없음. 루트 스크립트는 워크스페이스에 위임.
2. **어드민 스캐폴드.** `apps/admin`: Next.js 앱(같은 고정 canary),
   `packages/ui` 토큰 기반 어두운 운영 테마, 헬스 라우트, 빈 섹션(Stores /
   Inbox / Queue / Settings).
3. **어드민 인증.** `admin_users` + `admin_sessions` 마이그레이션, 첫 어드민용
   시드 스크립트, 로그인 페이지, 세션 미들웨어, 로그아웃. 공개 등록 없음.
4. **Vercel 연결.** `apps/admin`에 루팅된 두 번째 Vercel 프로젝트, Postgres env
   구성; 기존 프로젝트를 `apps/owner-app`으로 재루팅. 브랜치 매핑은 GitHub
   Flow를 따름(`main` → 프로덕션, PR별 프리뷰) — `feat/social-post-publishing`이
   `dev` 브랜치를 폐지하며 이 단계 전에 머지되어야 함. architecture.md §1에 따른
   프로젝트별 Ignored Build Step 규칙.
5. **듀얼-앱 e2e 하네스.** 두 개의 `webServer` 항목(owner-app + admin, 별개
   포트, 실행당 하나의 스텁 SQLite 파일)을 가진 루트 Playwright 설정; 교차-앱
   스펙은 `tests/e2e-cross/`에; 기존 단일-앱 스위트는 변경 없음.

병행 워크스트림(소유자: 창업자, 엔지니어링 아님): 우호적인 매장 2~3곳을 1주차부터
수동 서비스 — v1 앱 + 운영자 손 — 하며 모든 카카오 교환(메시지/답장 타임스탬프,
승인 결과)을 Phase 1 위젯 계측과 동일한 메트릭 정의로 기록. 실제 요청이 대시보드의
테스트 데이터가 되고; 기록된 교환이 전제-2 비교 베이스라인이 됩니다.

수용 기준:

- 레포 루트에서 기존 스위트 전체 그린: `typecheck`, `lint`, `test`, `build`,
  `e2e`(스텁 모드) — 이동이 아무것도 바꾸지 않았음을 증명.
- `npm ls react`가 워크스페이스 전체에서 정확히 하나의 React를 해석.
- 어드민 로그인 왕복이 스테이징 Neon에 대해 Vercel 프리뷰에서 작동; 오너 세션
  쿠키가 어떤 어드민 라우트에도 접근 불가하고 그 반대도 마찬가지(라우트
  테스트로 커버).
- 사소한 교차-앱 스펙이 듀얼-앱 하네스에서 통과.
- `npm run db:pg:verify`가 새 마이그레이션과 함께 통과.

초과 규칙: 분리가 1주를 넘으면 패키지 추출을 `packages/db`만으로 줄이고(어드민이
도메인/통합을 경로 별칭으로 임시 임포트) 나머지는 정리 PR로 미룸.

## Phase 1 — 채팅 MVP (휴먼 모드)

목표: 오너가 모서리 위젯에서 메시지를 보낼 수 있고; 운영자가 대시보드 인박스에서
응답하며; 모든 메시지가 활동 맥락을 실어 나른다.

태스크:

1. **마이그레이션:** `cs_conversations`, `cs_messages`, `cs_message_context`,
   `activity_events`.
2. **활동 트레일 훅** (오너 앱): `packages/domain`의 고정 액션 enum, 클라이언트
   링 버퍼, 주기적 플러시 엔드포인트.
3. **오너 채팅 위젯:** DESIGN.md에 따른 플로팅 버튼 + 패널(모바일 시트 / 사이드
   패널 ≥680px), 메시지 목록, 컴포저, 안 읽음 배지; 커서 엔드포인트로 3초 열림 /
   30초 닫힘 폴링.
4. **오너 채팅 API:** create-message(트레일 맥락 첨부, 레이트 리밋),
   list-messages(커서), mark-read. 전체적으로 매장-스코프 소유권 강제.
5. **대시보드 인박스:** 대화 목록(awaiting-reply 우선, 5초 폴링), **맥락
   패널**(메시지별 섹션/단계 + 최근-행동 트레일)을 가진 대화 뷰, 답장 컴포저,
   assign-to-me, resolve. 답장은 `author_kind='admin'`으로 쓰이고 오너에게는
   어시스턴트로 렌더링됨.
6. **감사:** 운영자 답장과 해결을 `audit_logs`에 로깅.

수용 기준:

- E2E(스텁, 두 앱 실행): 오너가 마케팅 화면에서 메시지 발송 → 운영자 인박스에
  5초 내 표시 **그리고** 섹션/단계 맥락 포함 → 운영자 답장이 위젯에 5초 내 표시
  → 읽음 시 안 읽음 배지 초기화.
- 트레일은 enum된 액션만 포함(스키마 검증); GBP-연결 화면에서 막힌 채 보낸
  메시지는 콘솔에서 그것을 눈에 띄게 보여줌.
- 유닛 커버리지: 대화 리포지토리, 맥락 첨부, 커서 페이지네이션, 레이트 리밋.
- 킬-메트릭 계측(전제 2, [design-decisions.ko.md](design-decisions.ko.md)): 주간
  활성화, 오너 응답 시간 중앙값, 오너 개시 대화 수를 `cs_messages`,
  `activity_events`, `cs_conversations`에서 계산 — 각 계산 단위를 픽스처 데이터에
  대해 유닛 테스트(깨진 메트릭은 4주차 전제 결정을 조용히 오염시킴). 승인-완료
  메트릭은 Phase 3에서 활성화.

## Phase 2 — AI 모드 + 매끄러운 핸드오프

목표: 운영자가 대화별로 "AI가 초안, 운영자가 발송" 태세를 켤 수 있고; 자율 AI
모드는 초안 품질이 신뢰되면 추가 대화별 플립; 운영자가 오너에게 보이지 않게
이어받고(다시 넘겨줄) 수 있다.

창업자 결정(2026-07-19, 원래의 "ai_draft 기본값"을 수정): 새 대화는 여전히
**`human`** 모드로 열림 — 초기 학습을 극대화하는 컨시어지 태세 — 이고, 운영자가
콘솔에서 대화를 `ai_draft`(그다음 `ai`)로 옵트인. 대화를 `human`으로 되돌리면
미발송 AI 초안을 폐기하는 대신 편집 가능한 초안으로 **유지**함.

실패-격하 정교화(PR2): 작성 실패는 모드별로 다름. 자율 `ai`는 루프에 운영자가
없으므로 오너가 정중한 오너-가시 폴백을 받고 **그리고** 대화가 플래그됨.
`ai_draft`는 이미 모든 답장을 운영자로 라우팅하므로 실패는 대화만 플래그(오너-가시
폴백 없음 — 운영자가 답장을 씀). 두 경로 모두 항상 플래그; 어느 쪽도 조용히 드롭
안 함.

태스크:

1. **`CsAssistant` 어댑터 계약** + 결정적 스텁 + OpenAI 프로덕션 구현(매장
   프로필, GBP 상태, 캠페인 상태, 메시지 트레일로부터 시스템 프롬프트).
2. **초안 태세:** `cs_messages`의 `draft` 상태(AI 작성, 오너 절대 비가시) +
   콘솔 초안 검토/편집/발송 화면. AI 작성은 오너 메시지가 저장된 후 대역 밖에서
   실행(architecture.md §5) — 절대 오너의 POST 안에서 안 됨. 모드 토글:
   대화별로 `human`(기본), `ai_draft`, 자율 `ai` 간 전환; 실패는 정중한 폴백
   메시지 + 대시보드 플래그로 격하(절대 조용히 안 함).
3. **핸드오프 시맨틱:** 휴먼으로 전환 시 AI 답장 즉시 중단; 다시 전환 시 재개.
   콘솔은 AI vs 어드민 작성자를 구별해 렌더링; 오너는 하나의 어시스턴트를 봄.

수용 기준:

- 스텁-모드 E2E: AI 대화가 결정적 답장을 생성; 대화 도중 휴먼으로 토글하면 다음
  메시지에 대해 AI 억제; 오너 트랜스크립트가 하나의 연속 어시스턴트를 보임.
- 프로덕션 OpenAI 경로에 대한 어댑터 request-spec 테스트(라이브 호출 없음), v1
  request-spec 패턴과 일치.
- 강제-실패 테스트: AI 오류가 폴백 메시지 + 플래그된 대화를 낳고, 오너는 절대
  오류 상태를 보지 못함.
- 초안-가시성 테스트: `draft`-상태 행이 어떤 오너-가시 읽기(list-messages, 안 읽음
  카운트, 배지)에도 절대 나타나지 않음 — 이 이음매가 원-어시스턴트 착시의
  전부임.

## Phase 3 — 마케팅 소재 파이프라인

목표: 완전한 루프 — 오너 업로드, 운영자 제작, 오너 승인, 대시보드가 여러
플랫폼에 게시.

태스크 4–5를 만들며 내린 결정(PR3):

- **최종 카피는 `campaign_requests.final_copy`에 존재**(마이그레이션 0010),
  가공 애셋의 `meta`가 아님. 카피는 요청별 — 한 캠페인이 모든 채널에 하나의 카피
  본문을 게시 — 이므로 애셋별 저장은 카디널리티가 틀리고 요청 수준 읽기에서 안
  보임.
- **상태 컬럼이 동시성 토큰이다.** 모든 전이가
  `UPDATE … WHERE id = ? AND status = <호출자가 읽은 상태>`를 하므로, 뷰가 오래된
  호출자는 0행에 매치되어 승자를 덮어쓰는 대신 졌다고 통보받음. 오너의 결정이 그
  가드와 `campaign_review_events` 삽입을 한 트랜잭션으로 감싸고, 이것이 중복
  제출이 정확히 한 행을 낳게 함. 도메인 전이 함수는 `packages/domain`에 남고 —
  `@glocalx/db`는 타입만 그것에 의존.
- **`ready_for_review`는 완성된 소재를 요구.** 상태 머신은 `in_production`이 합법
  소스 상태라는 것만 알므로, 라우트가 추가로 최소 하나의 가공 애셋 _과_ 최종
  카피가 존재하기 전까지 핸드오프를 거부 — 오너가 빈 승인 화면을 열어선 안 됨.
- **"변경 요청" 결정은 노트를 요구**(스키마 강제); `go`와 `no_go`는 아님. 운영자가
  할 것이 아무것도 없이 캠페인을 제작으로 되돌리는 건 유용한 상태가 아님.
- **오너-가시 결과 처리:** 종료됐거나 오래된 요청은 리뷰 카드를 닫고(각각 확인
  또는 충돌 메시지와 함께) 상태 목록을 새로고침; 그 외 오류는 카드를 열어 둬 오너가
  그냥 다시 탭할 수 있게 함.

태스크 6을 만들며 내린 결정(PR4 — 게시 패널):

- **`store_channel_links`는 태스크 7이 아니라 여기서 들어온다.** Instagram
  자격은 실제 매장별 링크 소스가 필요; 그것 없이는 패널이 "어댑터가 구성됨"만
  말할 수 있는데, 이는 같은 질문이 아님. 마이그레이션 0011이 테이블 추가(태스크
  7이 채우는 nullable `encrypted_token` 컬럼 포함); 태스크 6은 `status`만 읽으므로
  아직 토큰 저장/읽기 없음.
- **게시는 운영자의 요청 안에서 인라인으로 실행.** 운영자가 트리거하고 기다리는
  중이며, 두 채널 호출은 코호트 규모에서 함수 타임아웃 안에 넉넉히 들어감 —
  그래서 워커도 폴링 화면도 없음. 캠페인 자신의 `publishing` 상태가 진행 중 잠금:
  두 번째 클릭은 가드된 업데이트에 져서 레이스를 통보받음.
- **게시와 재시도가 한 라우트.** `POST …/publish`가 요청의 현재 상태에서
  `START_PUBLISHING`(from `approved`) 또는 새 `RETRY_PUBLISHING`(from `failed` /
  `partially_published`)를 골라, 콘솔이 어느 쪽인지 알 필요 없게 함.
  `RETRY_PUBLISHING`은 의도적으로 `published`와 `approved`에서 도달 불가.
- **선택된 채널 중 하나라도 부적격이면 실행 전체를 거부.** 패널이 부적격 채널을
  비활성화하므로, 그것을 지목하는 POST는 오래된 화면이거나 손수 만든 요청 —
  절반만 실행하면 캠페인이 차단된 채널에 대한 잡 없이 `publishing`에 남음.
- **진척은 이번 실행이 건드린 채널만이 아니라 요청의 모든 잡에서 계산**되므로,
  실패했던 한 채널을 고치는 재시도가 캠페인을 완전 게시로 정착시킬 수 있음.
- **멱등 키는 파생되며 절대 공급되지 않음** — `publish-<channel>-<requestId>` —
  이라 "시도 간 고정"이 호출자 관례가 아니라 구조적임.
- **`canUseLiveGbpActions`와 `token-encryption`이 `packages/domain`으로,
  GBP 게시-크레덴셜 읽기가 `packages/db`로 이동.** 운영자 측이 셋 다 필요; 오너
  앱은 옛 경로에서 재수출. 하나의 VERIFIED-전용 게이트와 하나의 크레덴셜 쿼리 —
  두 게시 경로가 드리프트할 수 없음.
- **오너는 채널 + 상태 + 타임스탬프만 봄.** 시도 횟수, 운영자-가시 실패 텍스트,
  채널 자신의 포스트 id는 운영자 측에 남음.

태스크 7을 만들며 내린 결정(PR5 — 조직 크레덴셜 배선):

- **캠페인 경로는 조직 계정에서 GBP를 게시; v1은 오너 토큰 유지.** 마이그레이션
  0012가 `org_credentials`(프로바이더별 고유) 추가, 캠페인 게시는 토큰을 위해
  `google_org`를 읽으면서 위치 `parent`는 여전히 매장 자신의 GBP 레코드에서 파생
  — 그래서 오너가 구글을 연결한 적 없는 매장도 게시 가능. v1 오너 컴포저는 손대지
  않으므로, 뒤집기가 출시된 경로에 회귀 리스크를 안 지움.
- **"리프레시 처리"는 detect-and-fail이지 리프레시 왕복이 아님.** 만료된
  크레덴셜은 잡을 운영자-가독 메시지로 실패시킴(architecture.md: "절대 조용한
  재시도 루프 없음"). 리프레시 토큰은 운영자가 의도적으로 로테이트할 수 있도록
  저장되지, 게시 경로가 만료를 넘어 재시도할 수 있도록이 아님. 60초 유예는 곧
  만료될 토큰을 이미 만료된 것으로 취급해, 그 실패를 불투명한 프로바이더 오류로
  표면화하는 대신 채널 호출의 우리 쪽에 둠.
- **크레덴셜 누락은 자격 게이트가 아니라 잡 실패.** 매장은 게시 가능; 조직이
  단지 연결 안 됐을 뿐. 자격은 매장에 관한 것(검증된 위치, 연결된 계정)으로
  남으므로, 구성 안 된 조직이 모든 매장의 패널을 차단으로 렌더링하지 않음.
- **세 가지 조회 결과, 분리 유지:** 없음, 복호화 불가, 발견됨. "복호화 못 함"을
  "하나도 없음"으로 뭉개면 진짜 결함이 로테이트된 `TOKEN_ENCRYPTION_KEY`일 때
  운영자를 토큰 재붙여넣기로 보내게 됨.
- **만료 게이트가 토큰을 반환.** `evaluateOrgCredentialState`는 `usable`
  브랜치에서만 크레덴셜을 돌려주므로, 어떤 호출자도 검사를 통과하지 않고 토큰에
  도달할 수 없음 — 불변식이 관례가 아니라 구조적.
- **Instagram은 매장 자신의 연결 계정으로 게시.**
  `store_channel_links.encrypted_token`이 이제 선택적 `account`로 어댑터에 도달;
  아직 토큰 없는 링크는 환경 계정으로 폴백하며, 이것이 스텁 모드와 v1 컴포저를
  불변으로 작동하게 함. 그 토큰을 읽는 것은 링크를 읽는 것과 별도 매장 메서드라,
  토큰 자료가 뷰 모델에 절대 들어가지 않음. `meta_app`은 저장 가능하나 안 읽음 —
  Instagram의 크레덴셜은 매장별이고, 앱-레벨 토큰은 Meta 심사를 기다림.
- **운영자는 Settings에서 크레덴셜을 붙여넣고; 무엇도 그것을 되읽지 않음.** 저장
  응답은 패널이 렌더링하는 것과 같은 요약 목록, 감사 행은 프로바이더와 만료 설정
  여부를 기록, 누락된 `TOKEN_ENCRYPTION_KEY`는 500이 아니라 이름 붙은 503 반환.

태스크 8을 만들며 내린 결정(PR6 — 채팅 링키지 + 운영자 넛지):

- **한 상태만 채팅 공지를 올림: `ready_for_review`.** 오너가 액션을 취해야 하는
  유일한 전이임; 제작·승인·게시를 같은 스레드에 서술하면 컨시어지 대화를 상태
  로그로 만들고 오너가 그것을 무시하도록 훈련시킴. (태스크 6의 게시 재시도-캡
  공지는 유효 — 그것도 오너에게 무언가, 즉 사람에 대한 인내를 요청함.) 공지는
  가드된 전이가 취해진 후에만 올려지므로, 레이스에서 진 운영자는 승자가 넘어간
  소재를 절대 알리지 않음.
- **넛지는 이벤트 행이 아니라 컬럼.** `campaign_requests.nudged_at`(마이그레이션 0013)은 한 질문에 답함 — 오너가 지금 있는 상태에 대해 여전히 개인 메시지를
  빚졌는가 — 이고 큐가 모든 카드에서 그것을 읽음. `campaign_review_events` 행이면
  누가·언제를 담겠지만, 큐가 불리언에 답하려고 트레일을 스캔해야 하고, 트레일은
  운영자의 워크리스트가 아니라 오너의 결정 이력임. 감사 로그가 이미 어느 운영자가
  표시했는지 기록함.
- **모든 상태 변경이 `nudged_at`을 초기화.** 넛지는 오너가 앉아 있는 상태를
  묘사하므로, 전이는 항상 그것이 속한 에피소드를 끝냄. 하나의 가드된 UPDATE 안에서
  초기화하면 어떤 호출자도 기억할 필요 없고, 제작을 거쳐 루프백한 캠페인은 두
  번째로 오너에 도달할 때 새 넛지를 올바르게 빚짐.
- **넛지 표시는 정확히 한 번.** 가드는
  `status = 'ready_for_review' AND nudged_at IS NULL`이라 더블클릭이 한 행과 한
  감사 항목을 쓰고, 진 쪽은 리로드하라고 통보받음 — 이 파이프라인의 다른 모든
  쓰기가 쓰는 상태-as-토큰 이야기와 동일. 라우트는 본문을 받지 않음: 운영자가 한
  사실을 단언하고, 서버가 시간을 찍고, 그들이 실제로 한 말은 오너와의 자신의
  스레드에 남음.

태스크:

1. **마이그레이션:** `campaign_requests`, `campaign_assets`,
   `campaign_review_events`, `publish_jobs`; `packages/domain`의 단일 전이 함수와
   전수 상태-머신 테스트.
2. **`MediaStore` 계약:** Vercel Blob 프로덕션 구현 + 파일시스템 스텁; 서명-URL
   렌더링; 업로드 한도(10 파일, 10MB, 이미지-타입 화이트리스트).
3. **오너 인테이크 화면:** 이미지 업로드 + 브리프 → `submitted`; 요청 상태
   타임라인 목록(v1 컴포저 화면 대체; 리뷰/실적은 스텁·라벨 유지).
4. **대시보드 제작 큐:** 상태 칸반; 원본 + 브리프가 있는 요청 상세; 가공-애셋
   업로드 + 최종 카피; `ready_for_review`로 이동.
5. **오너 go/no-go 화면:** 렌더링된 최종 소재; 승인 / 변경 요청(노트와 함께) /
   반려; 결정을 `campaign_review_events`에 기록하고 큐에 표면화.
6. **게시 패널:** 채널별 자격(v1 GBP 검증 게이트 + Instagram 링키지 검사 재사용),
   기존 게시 파이프라인을 통한 멱등 키가 있는 `publish_jobs`, 채널별 상태/이력,
   운영자 트리거 재시도(최대 3, architecture.md §2에 따라).
7. **조직 크레덴셜 배선**(architecture.md "조직 게시 크레덴셜"): `org_credentials`
   - `store_channel_links` 마이그레이션, 암호화 저장, `blocked_by_credentials`
     결과가 있는 게시-경로 리프레시 처리. 참고: 외부 선결 조건 — 조직 구글 OAuth
     클라이언트 + Meta 앱 심사 — 는 1주차 운영 태스크; Phase 3의 게시 수용은 어차피
     스텁 모드로 돌지만, 라이브 게시는 그들을 기다림.
8. **채팅 링키지 + 운영자 넛지:** 상태 변경이 매장의 대화에 어시스턴트 메시지를
   올림("소재가 검토 준비됐습니다"). v2에는 앱 외 알림이 없으므로, 큐는
   `ready_for_review`에서 명시적 넛지 단계도 추적 — 운영자가 오너의 기존 채널로
   직접 알리고 완료 표시; <1영업일 약속이 이 단계에 의존하고, 카카오 알림(v2.1)이
   바로 그것의 자동화.

수용 기준:

- 전체 루프의 스텁-모드 E2E: 업로드 → in_production → ready_for_review → go →
  두 채널 게시, 두 앱에 이력 가시; no_go 경로는 오너 노트를 첨부해 요청을 제작으로
  되돌림.
- 상태 머신이 불법 전이를 거부(전수 유닛 테스트); 오너 `go` 전에는 게시 불가능
  (라우트 + 도메인 테스트).
- 리플레이된 게시 요청이 (request, channel)별 멱등.
- 더블-제출 테스트: 빠른 중복 go/no-go 액션이 정확히 하나의
  `campaign_review_events` 행과 채널당 최대 하나의 게시 잡 생성.
- 오래된-화면 테스트: 아래에서 상태가 바뀐(예: 오너가 보는 동안
  `changes_requested`로 이동) 요청 승인이 명확한 오너-가시 메시지와 함께 전이
  함수에 의해 거부됨.
- 업로드 재검증 테스트: 클라이언트 토큰 흐름이 우회·남용됐어도 애셋 등록이
  서버측에서 초과 크기와 비화이트리스트 콘텐츠 타입을 거부.
- 재시도-캡 테스트: 3번째 실패 시도가 잡을 종료로 잠그고, 시도 간 멱등 키를 고정
  유지하고, 채팅 알림을 올림(architecture.md §2 재시도 정책에 따라).
- 클라이언트 응답의 Blob URL이 서명·만료됨; 원본이 절대 공개 리스트 가능하지
  않음.

## Phase 4 — GBP 조직-접근 온보딩

목표: 앱의 핵심 온보딩 약속 — 구글 로그인, GBP 연결, 조직 관리자 접근 — 이
추적되고 재개 가능한 흐름이 된다.

태스크:

1. **마이그레이션:** 운영자-주도, 감사되는 전이를 가진 `gbp_access_requests`(v2에
   자동 구글 폴링 없음 — architecture.md 참고; v1 검증 상태 머신은 계속 게시
   자격만 게이팅).
2. **오너 연결 흐름:** 로그인 후 GBP 연결 화면(v1 GBP OAuth 재사용) → 오너에게
   보이는 조직 접근 요청 상태(`invited/pending/granted`), 막다른 길 대신 "저희가
   처리 중" 상태와 함께; 막힌 상태는 채팅으로 딥링크. **채팅을 통한 운영자-지원
   승인이 첫 코호트의 주 경로**(설계 문서 전제 1,
   [design-decisions.ko.md](design-decisions.ko.md)); 셀프서브 흐름은 확장 경로.
3. **대시보드 가시성:** 매장별 연결 상태, 독촉 노트, 감사 로깅이 있는 수동 상태
   override(규정 외 승인용).

수용 기준:

- 스텁-모드 E2E: 신규 오너가 시뮬레이션 전이를 통해 `granted`에 도달; 모든 중간
  상태가 두 앱에서 올바르게 렌더링.
- 지연된 `pending` 매장이 대시보드 Stores 목록에 나이(age)와 함께 가시; 운영자
  노트 + override가 감사됨.
- 기존 v1 GBP 설정 테스트가 재배치된 도메인 코드에 대해 여전히 통과.

## 검증 게이트 (모든 단계)

1. 태스크 스펙에 대한 셀프 diff 리뷰; 위험하거나 보안을 건드리는 변경에는
   독립적 2차 의견으로 `/codex review`.
2. 루트에서 `npm run typecheck && npm run lint && npm run test` 그린.
3. `npm run e2e`(스텁) 그린; 새 흐름은 같은 PR에서 e2e 커버리지를 얻음.
4. 영향받은 화면에 대한 `/qa` 브라우저 패스(건드린 경우 두 앱 모두).
5. `main` 머지 전 `db:pg:verify`와 Vercel 프리뷰로 Postgres 마이그레이션 검증.

**Lane C** GBP 접근(Ph 4). A와 B는 병렬 워크트리 후보. 충돌 플래그: 모든 레인이
`packages/db`에 순서 있는 마이그레이션을 추가 — 마이그레이션 번호를 레인별로 미리
할당; A와 B 둘 다 `packages/domain`을 건드림 — cs/_와 campaign/_ 모듈을 분리
유지. A + B를 병렬 시작, 둘 중 하나가 머지되면 C.
