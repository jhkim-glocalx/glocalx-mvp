## 1. v2에서 무엇이 바뀌는가

v1은 마케팅 자동화 루프 전체를 오너용 앱 안에 넣으려 했습니다 — 정보 추출,
GBP 설정, AI 포스트 생성, 이미지 처리, 게시까지. v2는 제품을 의도적으로 둘로
나눕니다:

- **오너 앱 (v2)** — 최소한의 모바일 우선 화면. 오너는 구글로 로그인하고, 자신의
  구글 비즈니스 프로필을 연결해 GlocalX 조직 계정이 관리자 접근을 요청할 수 있게
  하고, 채팅 위젯으로 어시스턴트와 대화하고, 마케팅 소재(사진 + 무엇을 홍보할지
  짧은 설명)를 제출합니다. 완성된 소재를 승인하거나 반려합니다. 그게 전부입니다.
- **어드민 대시보드 (신규)** — 내부 운영 콘솔. 팀은 모든 매장, 모든 대화, 모든
  마케팅 요청을 봅니다. 운영자는 오너의 원본 사진을 게시 가능한 소재로 가공하고,
  오너 승인을 위해 되돌려 보내고, 승인된 소재를 조직 계정에서 여러 플랫폼에
  게시합니다. 채팅은 **AI 모드**(자동 응답) 또는 **휴먼 모드**(실제 운영자가
  응답)로 돌 수 있으며 — 오너는 항상 하나의 연속된 어시스턴트를 경험합니다.

오너 앱의 리뷰·실적 섹션은 계속 보이지만 **스텁 기반**입니다. 이들은 향후
워크스트림이며 v2 딜리버리 범위에서 명시적으로 제외됩니다.

## 2. 왜 컨시어지 운영을 먼저 하는가

이것은 의도된 "컨시어지 MVP" 전략입니다:

- **고객당 학습이 극대화됩니다.** 모든 마케팅 요청이 사람 운영자를 거치므로,
  어떤 개선 판단·카피 수정·채널 선택이 중요한지를 소프트웨어에 인코딩하기 전에
  정확히 봅니다.
- **범위가 붕괴합니다(줄어듭니다).** 오너 앱은 이미지 편집 UX, 개선 판단 흐름,
  채널 구성을 덜어냅니다 — v1에서 가장 어렵고 가장 검증이 덜 된 화면들입니다.
- **자동화는 재작성이 아니라 다이얼입니다.** 대시보드는 큐와 상태 머신을 중심으로
  만들어집니다. 각 수동 단계(채팅 응답, 이미지 개선, 채널 게시)는 확신이 쌓이면
  매장별로 독립적으로 자동화로 전환할 수 있습니다. AI/휴먼 채팅 토글이 이 패턴의
  첫 사례입니다.
- **v1 코드베이스는 버려지지 않고 재사용됩니다.** 인증, GBP 설정 오케스트레이션,
  게시 파이프라인(GBP + Instagram), OpenAI 어댑터, 스텁/프로덕션 통합 경계가 모두
  이어집니다.

## 3. v2 루프 (처음부터 끝까지)

```
Owner                          System                        Operations
─────                          ──────                        ──────────
Google login ──────────────▶ OAuth + session
Connect GBP ───────────────▶ org access request ──────────▶ track/assist grant
                                                             (manager access)
Chat (corner widget) ──────▶ conversation + context ──────▶ AI mode: auto-reply
  · carries activity trail     telemetry                     Human mode: operator
                                                             replies in console
Upload photos + brief ─────▶ campaign request queue ──────▶ operator produces
                                                             posting-ready material
Go / No-go review ◀──────── ready-for-review material ◀───┘
      │ go
      ▼
                             publish jobs ────────────────▶ operator triggers
                                                             multi-platform publish
Published confirmation ◀──── per-channel status              (GBP, Instagram, …)
```

이 루프에서 가장 중요한 두 가지 속성:

1. **오너 승인이 게시의 관문입니다.** 오너의 명시적 승인 없이는 무엇도 라이브로
   나가지 않습니다 (v1의 승인 정책에서 이어짐 — 완전 자동 게시 없음).
2. **맥락이 풍부한 지원.** 모든 채팅 메시지는 오너가 무엇을 하고 있었고 어디서
   막혔는지(화면, 단계, 최근 행동)를 실어 나릅니다. 그래서 운영자는 "지금 뭐가
   보이세요?"라고 묻지 않고도 진단할 수 있습니다.

## 4. v2의 성공 기준

- 신규 매장 오너가 구글 로그인 → GBP 연결 → 조직 접근 승인까지 엔지니어 개입
  없이 완료한다.
- 마케팅 요청이 오너 업로드에서 멀티플랫폼 게시까지 1영업일 이내에 진행되며,
  오너는 업로드와 go/no-go만 만진다.
- 운영자 한 명이 초기 고객 코호트(~10–20개 매장)를 대시보드만으로 무리 없이
  감당한다.
- 채팅 모드는 대화별로 AI와 휴먼 사이를 전환할 수 있으며 오너에게 보이는 이음매가
  없다.
- 모든 것이 기존 스텁/프로덕션 어댑터 경계 뒤에서 출시되어 데모와 QA가 라이브
  크레덴셜을 절대 요구하지 않는다.

## 5. 범위 요약 (엔지니어링)

범위 내:

- 모노레포 재구조화: `apps/owner-app`(기존 앱), `apps/admin`(신규), DB·도메인
  로직·통합을 위한 공유 `packages/*`. 하나의 Neon Postgres를 공유하는 두 개의
  Vercel 프로젝트.
- 어드민 인증(초대 전용, 역할 기반), 자체 세션 시스템 — 오너 앱과 쿠키를 공유하지
  않음.
- CS 채팅: 오너 앱의 플로팅 위젯, 대시보드의 대화 콘솔, 폴링 전송, 대화별 AI/휴먼
  모드, 메시지에 첨부되는 활동 맥락.
- 활동 텔레메트리: 오너 앱의 섹션/단계 브레드크럼.
- 마케팅 소재 파이프라인: 오너 인테이크(이미지 + 브리프) → 대시보드 제작 큐 →
  ready-for-review → 오너 go/no-go → 채널별 게시 잡 + 이력.
- GBP 조직 접근 온보딩: 구글 계정 연결, 관리자 접근 요청 상태를 승인까지 추적.

범위 밖 (명시적으로):

- 라이브 리뷰 조회/응답 및 실제 실적 분석 (계속 스텁).
- 자동 이미지 개선 (v2에서는 운영자가 자체 도구 사용).
- 결제, 청구, 구독 관리.
- 실시간 인프라(웹소켓/매니지드 realtime) — v2 전송은 폴링이며, 메시지 저장소는
  전송 방식에 무관하므로 이후 데이터 마이그레이션 없이 변경 가능.
- 네이버 스마트플레이스 게시 및 유료 광고 집행 (v1 범위에서 변동 없음).

## 6. 운영 모델

- **Claude**가 스펙 작성, 구현, 테스트, 검증, 출시를 담당합니다. **Codex**는
  요청 시 독립적인 2차 의견(설계 정합성 점검, `/codex review`)을 제공합니다 —
  구현은 하지 않습니다 (`CLAUDE.md` 참고).
- Git 흐름은 GitHub Flow입니다: `feat/*` PR을 `main`(프로덕션)에 직접 머지하고,
  PR별 Vercel 프리뷰가 스테이징 역할을 합니다 — `dev` 브랜치는
  `feat/social-post-publishing`으로 폐지됩니다. 어드민 앱은 같은 흐름에 연결된
  자체 Vercel 프로젝트를 갖습니다.
- `APP_INTEGRATION_MODE=stub`이 **두** 앱 모두에서 개발·리뷰·데모의 기본값으로
  유지됩니다.
