# 데모 워크스루 (스크립트) — GlocalX v2

> **English:** [demo-walkthrough.md](./demo-walkthrough.md)

투자자 또는 신규 운영자 코호트에게 GlocalX v2를 처음부터 끝까지 보여줄 때
쓰는 발표자용 스크립트입니다. **Phase 5 데모 시드**를 스텁 모드에서 구동하며
— 여기서 실제 Google·Instagram·Naver·OpenAI를 건드리는 것은 없습니다. 따라서
데모는 완전히 결정적이고 몇 번을 돌려도 똑같이 재현됩니다.

- **구동 대상:** `db:reset && db:seed`로 로드되는 데모 코호트
  ([ops-runbook.ko.md](./ops-runbook.ko.md)의
  시드 표 참고).
- **소요 시간:** 투자자용 컷 약 10분(Act 1–2), 운영자 교육용 컷 약 20분(콜아웃과
  마지막 리셋까지 포함).
- **두 개의 화면:** 모바일 **오너 앱**(`apps/owner-app`, :3000)과 어두운
  **운영자 콘솔**(`apps/admin`, :3100).
- **한 문장으로 각인시킬 것:** _"디지털 마케팅을 한 번도 안 해본 사장님이 그냥
  한국어로 대화하면, 운영자가 그것을 게시된 구글·인스타그램 포스트로 바꿉니다.
  파이프라인은 소프트웨어가 돌리고, 모든 판단은 사람이 합니다."_

## 발표 전 준비 (약 2분, 무대 밖에서)

Node 22 고정
(`export PATH=/Users/jaehun/.nvm/versions/node/v22.18.0/bin:$PATH`).

```bash
npm run db:reset && npm run db:seed          # 7개 매장 데모 코호트 로드 (SQLite)
ADMIN_SEED_EMAIL=ops@glocalx.example ADMIN_SEED_PASSWORD='demo-strong-pass' \
  ADMIN_SEED_NAME='Demo Operator' ADMIN_SEED_ROLE=OPERATOR \
  npm run seed:admin -w apps/admin           # 운영자 로그인 1개
```

> 운영자 콘솔은 자기 워크스페이스 DB(`apps/admin/.glocalx/dev.db`)를 읽습니다.
> Stores/Queue/Inbox가 비어 보이면 오너 앱 DB에 시드한 것입니다 —
> `GLOCALX_DB_PATH=<apps/admin/.glocalx/dev.db 절대경로> npm run db:seed`로
> 다시 시드한 뒤 같은 경로에 `seed:admin`을 실행하세요. (Phase 5 QA에서 실제로
> 걸렸던 함정입니다.)

두 서버를 모두 띄웁니다(`Bash`로 직접 띄우지 말 것 — 프리뷰 도구나 별도 터미널 2개):

```bash
npm run dev -- --hostname 127.0.0.1 --port 3000    # 오너 앱
npm run dev -w apps/admin                           # 운영자 콘솔 (:3100)
```

`APP_INTEGRATION_MODE=stub`인지 확인합니다. 브라우저 창 2개를 나란히 엽니다 —
오너 앱은 `http://127.0.0.1:3000`, 콘솔은 `http://127.0.0.1:3100`.

**데모용 로그인**

| 화면   | 방법                                                                                 |
| ------ | ------------------------------------------------------------------------------------ |
| 오너   | 루트 `/` → **구글로 시작**(스텁)이 데모 오너로 해석됨 → happy-path 매장으로 진입     |
| 오너   | 온보딩을 실시간으로 보여주려면: `/register`로 새 이메일 등록 → `NOT_STARTED` 새 매장 |
| 운영자 | `/login` → `ops@glocalx.example` / 위에서 시드한 비밀번호                            |

## Act 1 — 사장님 (모바일 오너 앱, 약 4분)

이 파트의 핵심: **사장님에게는 아무 수고가 없다.** GBP를 배우지도, 광고 플랫폼을
만지지도 않습니다 — 그저 한국어로 몇 개 질문에 답할 뿐입니다.

### 장면 1a — 맨바닥에서 온보딩 ("어, 이게 끝?" 순간)

1. 오너 앱 `/`를 엽니다. 진입 화면을 설명: _"소셜 계정이나 이메일로 시작"_
   — 버튼 3개, 카카오 / 구글 / 이메일. 이게 회원가입의 전부입니다.
2. **구글로 시작**(혹은 완전히 빈 매장을 보여주려면 새 이메일로 등록).
3. 워크스페이스에 진입합니다. 첫 탭이 **가게 인증 및 등록** — 이렇게 말합니다:
   _"저희는 사장님께 상호명만 받습니다. 나머지는 네이버에서 끌어옵니다."_
   스텁 모드에서는 네이버 사업자 정보 추출이 결정적 결과를 반환하므로, 사장님이
   타이핑하지 않아도 매장의 상호/주소/업종/영업시간이 채워집니다.
4. 매장을 확정합니다. 같은 탭의 **GBP 접근 카드**를 짚어줍니다 — 사장님은
   오직 세 가지 상태만 봅니다: **진행 중 / 완료 / 확인 필요** — 그 뒤의 여섯 개
   운영자 상태는 절대 보지 않습니다. _"사장님은 '진행 중'만 보면 됩니다. 구글
   권한의 복잡함은 운영자가 대신 처리합니다."_

> **토크트랙:** v2에서 사장님이 할 일의 전부는 — 상호명을 말하고, 저희가 찾은
> 내용을 확인하고, 필요할 때 대화하는 것. 구글이나 광고 플랫폼과 관련된 모든
> 일은 컨시어지(운영자 대행) 업무입니다.

### 장면 1b — 정상 운영 상태 (happy-path 매장으로 로그인)

데모 오너로 전환(**구글로 시작**)하면 완전히 완료된 매장 **브런치모먼트 홍대점**
(`demo-store`)으로 진입합니다.

1. **가게 인증 및 등록:** GBP 접근이 **완료**, 위치는 VERIFIED.
2. **마케팅 소재 요청:** 사장님이 요청한 캠페인을 보여줍니다 — 이 브리프가
   Act 2에서 운영자 업무가 됩니다.
3. **여러 SNS 자동홍보 / 홍보 콘텐츠 넣기:** **게시된** 포스트를 보여줍니다
   (구글 비즈니스 프로필과 인스타그램 양쪽에 나갔습니다). _"사장님이 요청하면,
   운영자가 제작하고, 승인 후 여러 채널에 한 번에 게시됩니다."_
4. **주간 홍보 실적 / 홍보 실적 자세히 보기:** 실적 화면 — 사장님이 실제로
   신경 쓰는 결과물. (스텁 지표, 결정적.)

Act 2로 넘어가는 연결 멘트: _"사장님 쪽은 이게 전부입니다. 이제 이 요청들이
운영자 콘솔에서 어떻게 처리되는지 보시죠."_

## Act 2 — 운영자 (어두운 콘솔, 약 5분)

이 파트의 핵심: **운영자 한 명이 눈에 보이는 파이프라인을 통해 여러 매장을
굴리고, 모든 전진은 의도된 사람의 행동이다** — 이것이 한계가 아니라 컨시어지
학습 루프입니다.

`:3100/login`에서 로그인합니다. **Stores**로 진입합니다.

### 장면 2a — Stores: 모든 상태에 걸친 GBP 접근

Stores 콘솔은 각 매장의 구글 비즈니스 프로필에 대한 조직 관리자 접근 요청을
처리합니다. 각 상태에 하나씩 놓인 시드 코호트를 훑어봅니다:

| 매장            | 상태        | 설명                                                |
| --------------- | ----------- | --------------------------------------------------- |
| 동네빵집 망원점 | **Invited** | 초대 발송, 사장님 수락 대기                         |
| 헤어살롱 연남점 | **Pending** | 사장님 수락함, 구글 처리 대기                       |
| 필라테스 합정점 | **Granted** | 게시 가능한 접근 확보                               |
| 카페 홍대입구점 | **Blocked** | 사장님이 초대를 못 찾음 → 채팅으로 라우팅 (2c 참고) |

두 종류의 컨트롤과 왜 분리돼 있는지 보여줍니다:

- **자연스러운 액션**(Send invite / Mark pending / Grant / Revoke / Block)은
  정상 진행 경로를 따라갑니다 — _"흐름이 진행됨."_
- **Override**는 감사 대상 비상 탈출구입니다 — 어떤 목표 상태든 직접 지정해
  규정 외 정정을 합니다. _"감사 로그가 '흐름이 진행됨'과 '운영자가 강제로
  바꿈'을 구분합니다."_ 이유는 **Save note**로 기록합니다.

### 장면 2b — Queue: 캠페인 파이프라인을 칸반으로

**Queue**를 엽니다. 각 카드는 하나의 캠페인 요청이고, 컬럼은 그 상태입니다.
시드는 모든 컬럼에 카드를 하나씩 놓아둡니다:

| 컬럼                  | 데모 매장           | 할 일                                              |
| --------------------- | ------------------- | -------------------------------------------------- |
| **Submitted**         | 동네빵집 망원점     | 집어들기 → 제작으로 이동                           |
| **In production**     | 헤어살롱 연남점     | 소재 제작, 최종 카피 작성                          |
| **Awaiting owner**    | 필라테스 합정점     | 이미 **넛지함** — "Owner notified" 스탬프 보여주기 |
| **Changes requested** | 카페 홍대입구점     | 노트 읽고 수정                                     |
| **Publishing**        | 분식상회 상수점     | **부분 게시** — GBP 성공, 인스타그램 실패          |
| **Settled**           | 브런치모먼트 홍대점 | 양쪽 채널 게시 완료 — 최종 상태                    |

여기서 반드시 짚을 두 가지 — 제품의 척추입니다:

1. **오너 넛지.** v2에는 **푸시 채널이 없습니다.** _Awaiting owner_ 카드는
   운영자가 카카오톡/전화로 사장님에게 연락하고 그것을 기록하기 전까지 움직이지
   않습니다. 넛지 스탬프가 **없는** 카드가 최우선입니다.
   _"자동 알림이 없습니다 — 이게 의도된 컨시어지 접점입니다."_
2. **재시도 캡.** 분식상회 상수점은 _부분 게시_ 상태: GBP는 성공했지만
   인스타그램 링크가 만료되어 실패했습니다. 게시는 채널별로 이뤄지고,
   **운영자가 재시도하며 절대 자동이 아니고**, **3회 시도**
   (`publishJobMaxAttempts`) 후 최종 상태로 잠깁니다. 실패한 잡의 `last_error`를
   보여줍니다.

### 장면 2c — Inbox: 사장님에게는 하나의 어시스턴트, 뒤에는 사람의 이음매

**Inbox**를 엽니다. 사장님은 항상 하나의 "어시스턴트"만 봅니다. 각 답장을 실제로
누가 쓸지는 운영자가 정합니다. 세 가지 태세를 모두 보여줍니다:

| 매장            | 모드          | 설명                                                          |
| --------------- | ------------- | ------------------------------------------------------------- |
| 김밥천국 신촌점 | **Human**     | 운영자가 모든 답장을 씀 — 컨시어지 기본값                     |
| 헤어살롱 연남점 | **AI draft**  | AI가 답장을 초안, **미발송** — 운영자 검토 후 **Send draft**  |
| 카페 홍대입구점 | **flagged ⚑** | 지금 사람 필요(사장님이 GBP 초대에서 막힘) → **Assign to me** |

AI 초안 이음매가 스토리입니다: _"AI가 초안을 쓰지만, 운영자가 보내기 전까지
사장님은 절대 보지 못합니다. 사람이 판단을 유지하면서 속도만 AI로 얻습니다."_
그런 다음 카페 홍대입구점의 플래그를 Stores의 **Blocked** GBP 상태와 연결합니다
— 같은 사장님, 두 콘솔에 걸친 하나의 일관된 문제.

## 클로징 (약 1분)

오너 창의 실적 화면으로 돌아옵니다.

> _"사장님은 상호명 하나로 시작해서 게시된 포스트와 실적을 봅니다. 운영자 한 명이
> 여러 매장의 파이프라인을 눈으로 보며 굴립니다. 오늘 데모는 전부 결정적 스텁 위에서
> 돌았습니다 — 실제 채널 연동은 크레덴셜을 꽂고 채널별로 검증하면 그대로 라이브가
> 됩니다."_

"이거 실제로 돌아가는 거예요?"라고 물으면 정직하게 답하세요 — **스테이징은
설계상 `APP_INTEGRATION_MODE=stub`로 돕니다.** 프로덕션 어댑터는 존재하며
안전하게 실패합니다(`blocked_by_credentials`). 라이브 전환은 채널별 크레덴셜 +
프리뷰 검증 단계이며,
[v2-production-cutover.ko.md](../deployment/v2-production-cutover.ko.md)에
문서화돼 있습니다.

## 예상 질문

- **"게시가 실패하면 어떻게 되나요?"** → Queue 2b: 채널별, 운영자 재시도,
  3회 캡, 한 채널만 성공 시 `partially_published`. 분식상회 상수점을 가리키세요.
- **"사장님은 어떻게 알림을 받나요?"** → 설계상 푸시 없음. 운영자가 사장님이
  이미 쓰는 채널로 넛지하고 큐가 그것을 추적합니다(2b).
- **"AI가 제 고객이랑 대화하나요?"** → 운영자가 대화를 AI-draft/auto로
  전환하지 않는 한 아닙니다. 기본값은 Human이고 AI 초안은 검토 없이 발송되지
  않습니다(2c).
- **"운영자 한 명이 얼마나 감당하나요?"** → 이 코호트가 측정하려는 바입니다.
  [ops-runbook.ko.md](./ops-runbook.ko.md)의 SLA가 시작
  가설입니다.
- **"완벽하지 않은 매장을 보여주세요."** → 코호트 전체가 그렇습니다: 접근 Blocked,
  수정 요청, 실패한 채널, 미발송 AI 초안.

## 실행 간 리셋

```bash
npm run db:reset && npm run db:seed
```

멱등하며 dev 서버가 DB를 잡고 있어도 안전합니다. `ensure*` 헬퍼보다 앞선 스키마의
경우 서버를 멈추고 `rm -rf .glocalx`를 먼저 하세요(CLAUDE.md § Known risks 참고).
