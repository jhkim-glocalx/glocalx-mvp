## 문제 정의

한국 소상공인 매장 오너는 로컬 마케팅(구글 비즈니스 프로필, Instagram)이
필요하지만 마케팅 소프트웨어를 스스로 운영하지는 않을 것입니다. GlocalX v1은 완전한
셀프서브 루프 — OAuth, 네이버 추출, GBP 설정, AI 포스트 생성, 게시 — 를 만들었고,
창업자들은 오너가 그것을 몰지 않을 거라고 결론 내렸습니다. v2는 제품을 나눕니다:
최소 오너 앱(구글 로그인, GBP 조직-접근 승인, 모서리 채팅 어시스턴트, 사진+브리프
인테이크, go/no-go 승인)과, 운영자 + AI가 소재를 제작해 조직 계정에서 여러
플랫폼에 게시하는 내부 어드민 대시보드. 서비스가 결과를 전달하고, 오너는 업로드와
승인만 만집니다.

## 수요 증거

얇으며, 그렇게 명명합니다. 증거는 부정형(negative-shaped)입니다: v1이 존재하고
창업자들의 판단은 오너가 셀프서브하지 않으리라는 것입니다(최소-노력 채팅-우선
흐름을 향한 CEO의 6월 범위 정렬과 일치). 아직 지목된 오너도, 결제도, 사용 급증도
없습니다. 아래의 병행-서비스 수정안은 정확히 이것을 2주 안에 믿음에서 행동으로
전환하기 위해 존재합니다: 우호적인 매장 2~3곳을 수동으로 서비스하며, 실제 사진을
받고, 실제 포스트를 게시하고, 실제 응답 지연을 측정합니다.

## 현 상황(Status Quo)

오너들은 마케팅을 전혀 안 하거나(방치된 GBP 리스팅, 카메라 롤에 잠든 사진), 마감
후 세 개의 콘솔(GBP, 네이버 스마트플레이스, Instagram)을 저글링합니다. 에이전시는
있지만 더 큰 사업체에 맞춰 가격과 형태가 잡혀 있습니다. 한국 매장 오너의 현실적
우회책은 "Canva 잘 쓰는 조카" 아니면 아무것도 안 하는 것입니다.

## 타깃 유저 & 가장 좁은 쐐기(Wedge)

클레임 가능한 GBP 리스팅과 매장 사진이 든 카메라 롤을 가진 한국 로컬 매장
오너(카페, 식당, 살롱). 쐐기: 그들은 사진 + 한 문장의 의도를 건네고; GlocalX는
원탭 승인용 완성된 포스트를 돌려주고 마땅히 가야 할 모든 곳에 게시합니다. 첫
코호트는 운영자 한 명이 서비스하는, 손으로 고른 10~20개 매장입니다.

## 전제(Premises)

1. **GBP 조직-접근 승인**(오너가 GlocalX 조직 계정에 관리자 접근을 부여) — 완화책과
   함께 합의: 채팅을 통한 운영자-지원 승인이 첫 코호트의 _주_ 경로이고, 셀프서브
   흐름은 확장 경로. `pending`은 대시보드 가시성과 독촉 노트를 가진 일급의 장기
   상태.
2. **CS에는 인앱 채팅이 카카오톡보다 낫다** — 킬 메트릭과 함께 합의(Codex가 이를
   도전; 해소는 아래): 계획대로 위젯을 출시하되, 주간 활성화, 오너 응답 시간
   중앙값, 승인 완료율, 오너 개시 대화 수로 계측. 계측 소스: `cs_messages`
   타임스탬프(응답 시간), `campaign_review_events`(승인 완료), `activity_events`
   (활성화), `cs_conversations`(오너 개시 수). 킬 임계값: 카카오의 응답 시간
   중앙값이 ~2배 빠르거나, 카카오의 승인 완료가 위젯보다 ≥20%p 높으면 전제가
   죽습니다; 활성화와 오너 개시 수는 킬 임계값 없는 맥락-전용 신호. 비교 방법:
   수동-서비스 매장들이 코호트 온보딩 시 위젯으로 이전하며 각각 전/후 창을
   제공하고, 4주차 평가는 서로 다른 매장을 비교하는 대신 이전된 각 매장의 카카오
   주간을 위젯 주간과 비교(같은 매장, 두 arm). 카카오 주간 동안 운영자는 모든
   교환을 공유 시트에 기록 — 오너 메시지 타임스탬프, 답장 타임스탬프, 승인
   요청/응답/결과 — 위젯 계측과 동일한 메트릭 정의를 사용해 베이스라인을 기억이
   아니라 측정합니다. 전제가 죽으면 v2.1이 카카오 알림/CS를 추가합니다.
3. **빌드-후-서비스 순서** — 병행-서비스로 수정: 우호적인 매장 2~3곳을 1주차부터
   수동으로 서비스(v1 앱 + 운영자 손)하며 빌드를 진행하고, 그들의 실제 요청이
   대시보드의 테스트 데이터이자 전제-1/전제-2의 증거가 됩니다.
4. **오너는 셀프서브하지 않는다**(v2가 존재하는 이유) — 수용; v1 자신의 궤적이
   증거입니다.
5. **v1 재사용은 실재한다** — 코드로 검증: 게시 파이프라인(GBP + Instagram, 멱등,
   이력 보존), GBP 상태 머신, OAuth, 어댑터 경계 모두 이어집니다.

## 교차-모델 관점

Codex(gpt-5.6, 새 컨텍스트, 읽기 전용 레포 접근) 콜드 리드:

1. **스틸맨:** "또 하나의 SMB 마케팅 도구가 아니라, 소프트웨어 레버리지를 가진
   사람-운영 로컬-마케팅 서비스를 만들어라. 오너는 사진, 맥락, 승인을 제공하고;
   운영자는 AI와 기존 게시 파이프라인을 사용해 결과를 전달하며, 그동안 제품은 어떤
   운영 단계가 자동화될 가치가 있는지 학습한다."
2. **가장 드러내는 결정:** 운영자-지원 승인 완화책 — "사람의 지원이 제품의 컨트롤
   플레인이다. 운영자 콕핏과 가이드된 오너 태스크를 먼저 만들어라; '연속 AI
   어시스턴트'는 처음엔 매니지드 서비스 전달을 둘러싼 세련된 인터페이스다."
3. **도전받은 전제:** 인앱 채팅 vs 카카오톡(해소는 전제 §2에 기록 — 킬 메트릭과
   비교 arm과 함께 유지).
4. **48시간 프로토타입:** 기존 앱 안의 얇은 수직 슬라이스 하나(모노레포 분리 없음,
   별도 Vercel 프로젝트 없음, 자율 AI 모드 없음); AI가 초안, 운영자가 발송; 매장
   한 곳을 수동 온보딩해 실제 포스트 하나를 처음부터 끝까지 게시.

종합: Codex의 얇은-슬라이스 직관은 Approach A로 채택됐고, "AI가 초안, 사람이 발송"
태세는 권장 접근의 Phase 2 시작 지점으로 접혔습니다. 모노레포-스킵은 크레덴셜 격리
근거로 거부됐습니다(조직 게시 토큰이 공개 앱 배포에 실려서는 안 됨).

## 검토한 접근들

### Approach A: 얇은 슬라이스 (단일 앱, /admin 라우트)

모노레포 분리 없음; 기존 앱 안에 어드민 라우트 그룹 + 별도 어드민 인증. 노력
M(사람 ~3주 / CC+Codex ~1.5주), 리스크 중. 서비스된 고객까지 가장 빠르고 재구조화
리스크 제로 — 하지만 조직 게시 크레덴셜과 운영자 도구가 공개 앱 배포에 실리고,
세션 격리가 경계가 아니라 관례이며, 분리는 이후 코호트 부하에서 다시 하게 됩니다.

### Approach B: v2 계획, 수정됨 (권장)

모노레포, 두 개의 Next.js 앱, 두 개의 Vercel 프로젝트, 공유 Neon Postgres, 여섯
단계(docs/v2/delivery-plan.md) — 그리고 이번 세션의 네 가지 수정: (1) 1주차부터
매장 2~3곳 병행-서비스; (2) 운영자-지원 GBP 승인을 주 경로로; (3) 수동 코호트를
비교 arm으로 하는 채팅 킬 메트릭; (4) 채팅 시작 태세로 "AI가 초안, 사람이 발송" —
자율 AI 모드를 빌드가 아니라 플립으로 만듦. 노력 L(사람 ~6주 / CC+Codex ~3-4주),
리스크 저-중.

### Approach C: 콕핏-우선 재정렬

B와 같은 최종 상태지만 대시보드를 변경 없는 v1 앱에 대해 먼저 만들고; 오너-앱
변경은 마지막. 2주차에 운영자에게 도구를 주지만, 초기 CS를 카카오톡으로 강제 —
전제-2 실험을 조용히 미리 결정 — 하고, 서비스 약속이 의존하는 인테이크/승인 루프를
지연시킵니다.

## 권장 접근

**Approach B.** 분리 결정은 크레덴셜 격리를 위해 이미 의도적으로 내려졌고; 계획
문서(docs/v2/README.md, architecture.md, delivery-plan.md)가 수용 기준과 함께
존재하며; 네 수정안이 계획의 두 실질 약점을 닫습니다 — 6주차까지 고객 접촉
없음(병행-서비스로 해결)과 측정되지 않은 채팅 베팅(킬 메트릭으로 해결). Phase
0(분리)은 고객 가치를 만들지 않으므로 엄격히 1주로 타임박스해야 합니다.

구현 전 docs/v2/에 접어 넣을 네 개의 세션 수정 + 하나의 정합:

- delivery-plan.md Phase 1과 3: 수용 기준에 채팅 킬 메트릭 추가(정의와 임계값은
  전제 §2). 응답 시간, 활성화, 오너 개시 수는 Phase 1에서 계측(`cs_messages`,
  `activity_events`, `cs_conversations`); 승인 완료율은 `campaign_review_events`가
  들어오는 Phase 3에서 활성화 — Phase 1은 측정 불가.
- delivery-plan.md Phase 2 + architecture.md §2/§5: 시작 태세는 "AI가 초안,
  운영자가 발송." 이는 현재의 2-모드 스키마가 표현할 수 없는 세 번째 대화 상태이며
  — `cs_messages`의 `draft` 상태(AI 작성, 오너 비가시), 콘솔의 초안 검토/편집/발송
  화면, 발송 액션을 요구합니다. Phase 2에 범위를 추가(대략 +2-3일); 초안 품질이
  신뢰되면 자율 `ai` 모드는 대화별 플립이 됩니다.
- delivery-plan.md Phase 4: 운영자-지원 승인이 주 온보딩 경로; 셀프서브 흐름은 확장
  경로.
- delivery-plan.md: Phase 0-병행 워크스트림 추가 — 엔지니어링이 아니라 명시적
  소유자(창업자)와 함께 "1주차부터 매장 2~3곳 수동 서비스".
- (하우스키핑, 리뷰에서 — 세션 수정 아님) README.md §6, architecture.md §1,
  delivery-plan.md(작업 모델 + Phase 0 수용): 모든 `dev`-브랜치 참조를 GitHub
  Flow와 정합 — `feat/social-post-publishing`이 `dev` 브랜치를 폐지하는 커밋
  f89fbc0을 담으므로, Phase 0의 "dev-branch Vercel preview" 수용 기준과
  브랜치-매핑 표는 Phase 0가 두 번째 Vercel 프로젝트를 연결하기 전에 `main` +
  PR별 프리뷰에 맞춰 다시 써야 합니다.

Phase 0 초과 규칙: 분리가 1주를 넘으면 패키지 추출을 `packages/db`만으로
줄이고(어드민 앱은 도메인/통합을 오너 앱에서 경로 별칭으로 임시 임포트) 나머지는
정리 PR로 미룹니다 — 재구조화 작업이 Phase 1을 잡아먹게 두지 마세요.

## 열린 질문

- v2 범위의 Instagram: 첫날부터 멀티플랫폼 게시를 유지할까, 아니면 GBP 단독으로
  루프를 먼저 증명하게 둘까(Codex 제안)? v1 파이프라인이 이미 둘 다 지원하므로
  현재 범위 내.
- 어드민 앱 커스텀 도메인 + 접근 강화 시점(첫 유료 코호트 전).
- v2.1 빠른 후속으로서의 카카오톡 알림: 알림 어댑터 계약을 지금 미리 만들까, 킬
  메트릭 결과를 기다릴까?

## 성공 기준

- 신규 매장이 엔지니어 개입 없이 `granted` GBP 접근에 도달한다(운영자 개입은
  허용되고 기대됨).
- 오너 업로드 → 멀티플랫폼 게시가 1영업일 이내, 오너는 업로드와 go/no-go만 만짐.
- 운영자 한 명이 10~20개 매장 코호트를 대시보드만으로 서비스한다.
- 코호트 서비스 1주차부터 채팅 킬 메트릭을 주간 수집; 4주차에 전제 2를 명시적으로
  재평가.
- 두 앱 모두 스텁 모드에서 완전히 데모 가능.

## 배포 계획

기존 Vercel 파이프라인의 웹 서비스(두 프로젝트). 브랜치 매핑은
`feat/social-post-publishing`이 들어오면 GitHub Flow를 따름: `main` → 프로덕션,
리뷰용 PR별 프리뷰(`dev` 브랜치 없음). 새 아티팩트 타입 없음 — 기존 배포
