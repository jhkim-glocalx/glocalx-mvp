# Design: Responsive Admin Console

## Problem Statement

The Admin console is difficult to read and operate at narrow widths. The global
stylesheet sets `html { min-width: 960px }`, the shell always reserves a 220px
sidebar, Inbox always uses a 300px list plus detail split, and Queue always
renders five columns. The result is clipped content, forced horizontal
scrolling, and controls that move outside the usable viewport on phones and
small desktop windows.

The operator's requested experience is explicit: keep the left navigation on
wide screens, make it toggleable on narrow screens, and let every Admin route
adapt to its available width.

## Demand Evidence

- The product is deployed and being used for live visual QA on the production
  Admin page.
- The operator identified a cross-screen symptom: the UI is generally hard to
  see at the available width, not just one isolated component.
- The requested behavior is specific: “왼쪽 사이드 패널이 토글이었으면 좋겠고
  너비에 맞춰서 반응형이었으면 좋겠음.”

## Status Quo

The current layout assumes a wide desktop viewport. The sidebar is permanently
visible, the main content has no max-width or narrow-width strategy, Inbox keeps
two panes side by side, and Queue keeps five status columns side by side. The
operator must tolerate clipping or horizontal scrolling when the viewport is
too narrow.

## Target User & Narrowest Wedge

The target user is an operator who uses the Admin console across production
workstations and occasionally narrower laptop or mobile-sized viewports. The
narrowest useful release is a complete responsive pass across the Admin shell
and all six routes: `/stores`, `/queue`, `/inbox`, `/posts`, `/users`, and
`/settings`.

## Constraints

- Preserve existing route behavior and operator workflows.
- Keep the current dark ops visual language and Korean labels.
- Do not make mobile read-only; operators must still be able to reply, approve,
  change state, upload, and publish where those actions already exist.
- Avoid introducing a component framework solely for responsive behavior.
- Maintain keyboard access, visible focus, ESC-to-close drawer behavior, and
  usable touch targets.
- Verify at compact phone, tablet, small laptop, standard desktop, and wide
  desktop widths.

## Viewport Model

| Class    | Width      | Shell                                                             | Content rule                                                   |
| -------- | ---------- | ----------------------------------------------------------------- | -------------------------------------------------------------- |
| Compact  | 0–767px    | Sidebar hidden; menu button opens modal drawer                    | Single-column task flow; only local regions may scroll         |
| Medium   | 768–1099px | Sidebar hidden by default; menu button opens a 280px modal drawer | Collapse panes when either would be below 320px                |
| Expanded | 1100px+    | Persistent 220px sidebar                                          | Multi-pane layouts are allowed when each pane remains readable |

These are starting thresholds. Acceptance widths are 360px, 390px, 768px,
1024px, 1280px, and 1440px.

## Premises

1. Wide screens should keep a persistent left navigation; compact screens should
   use a modal drawer opened by a visible toggle.
2. The global `min-width` and fixed multi-column assumptions are the primary
   causes of the current failure and must be removed rather than masked.
3. Every major operator task should remain completable on mobile, with lists and
   detail panels changing to a single-column flow when needed.
4. The responsive pass covers the entire Admin surface, not only `/stores`.
5. Success means no unintended page-level horizontal scrolling and no clipped controls,
   while reading, navigation, status changes, replies, approvals, and uploads
   remain usable.

## Cross-Model Perspective

Current responsive navigation guidance supports adapting navigation by available
width: persistent navigation on expanded screens and a drawer or compact
navigation treatment on smaller screens. This aligns with the requested sidebar
toggle and supports a consistent mental model across devices.

## Approaches Considered

### Approach A: CSS-centered patch

Remove the global minimum width, add a mobile drawer, and add a few route-level
media queries while keeping the current component structure. This ships fastest
but risks accumulating screen-specific exceptions.

### Approach B: Adaptive Admin Shell plus route layout rules

Make `OpsShell` the responsive foundation with a persistent desktop sidebar and
the same modal drawer on Compact and Medium widths. Define shared breakpoints and
spacing rules, then give each route an explicit narrow-width behavior: cards for
stores and settings, stacked list/detail for Inbox, and a readable board-to-list
transition for Queue. This is the recommended approach.

### Approach C: Mobile operations mode

Treat mobile as a distinct task-oriented mode with list-to-detail workflows,
sticky primary actions, and more aggressive content prioritization. This may be
the best mobile experience but creates a larger divergence between desktop and
mobile UI.

## Recommended Approach

Choose Approach B.

1. Establish layout primitives in `apps/admin/src/app/globals.css`:
   remove `html` minimum width, add width-safe page padding, use `minmax(0, 1fr)`
   for grid children, and define compact/medium/expanded breakpoints.
2. Extend `apps/admin/src/app/_components/ops-shell.tsx` with a menu toggle,
   drawer state, overlay, close behavior, and a shared navigation list. The
   desktop sidebar remains visible above the expanded breakpoint. The same
   modal drawer is used throughout Compact and Medium widths. The drawer
   closes after navigation, on overlay click, and on Escape. While open, focus
   is contained in the drawer, `aria-expanded` and `aria-controls` describe the
   toggle relationship, the drawer has an accessible name, and focus returns to
   the toggle after close.
3. Make `/stores` the first route acceptance surface. Keep cards full width,
   let long store names and selectors wrap, and make action groups stack without
   shrinking controls below a usable size.
4. Adapt `/inbox`: two columns on expanded screens; list and detail become a
   single flow on compact screens. Preserve selected conversation state and make
   the return-to-list action obvious.
5. Adapt `/queue`: on Compact and Medium widths, use a horizontally scrollable
   board inside an explicitly labelled local scroll region, with the selected
   request detail stacked below it. On Expanded widths, retain the five-column
   board. The detail and actions must remain readable and wrap.
6. Adapt `/posts`, `/users`, and `/settings` using the same width, card, form,
   and action-group primitives. Required compact workflows are: read a post and
   open its published link; inspect users and deactivate a user; inspect settings,
   view credential status, and submit the existing credential form. No route
   should require a page-wide minimum width.
7. Add Playwright visual and interaction coverage at all six acceptance widths.
   Store screenshots with the existing cross-app suite in `tests/e2e-cross` and
   run them with `npm run e2e:cross`; use Vitest for Admin unit/API coverage via
   `npm run test`. Add tests for drawer state transitions, route navigation,
   form controls, and key operator actions.

## Route / Action Acceptance Matrix

| Route       | Compact behavior                                              | Must remain usable                                                                |
| ----------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `/stores`   | Full-width cards; action groups wrap                          | Select listing, change state, reject, edit note                                   |
| `/inbox`    | Conversation list and detail are one-at-a-time                | Select, read, switch mode, edit draft, reply                                      |
| `/queue`    | Local-scroll board, stacked detail                            | Select request, upload, review, CTA, nudge, publish                               |
| `/posts`    | Single-column post list                                       | Read inline copy and open a published link only when a safe HTTPS URL exists      |
| `/users`    | Stacked user rows                                             | Inspect and deactivate user                                                       |
| `/settings` | Stacked metrics, credential, orphaned-upload, and form panels | Read metrics, inspect credentials, operate orphaned uploads, submit existing form |

## Must Ship / Follow-up

Must ship: responsive shell and drawer, removal of page-wide minimum width,
route layouts for all six pages, the Queue local-scroll decision, keyboard and
touch accessibility, and the full viewport acceptance matrix.

Follow-up: iconography or navigation information-architecture changes, a
separate mobile-only visual language, and new filtering or pagination behavior.

## Open Questions

- For Queue on a phone, the default is a horizontally scrollable five-column
  board inside a local scroll region. Revisit only if real card density makes
  that comparison unusable in visual QA.
- Should the mobile drawer show all six destinations or promote only the most
  frequent operational sections while keeping the rest under “더보기”? Default:
  show all six to preserve discoverability.
- Should the selected Inbox conversation persist through route changes or only
  within the Inbox view? Default: preserve current behavior and add only the
  responsive navigation affordance.

## Success Criteria

- At 360px, 390px, 768px, 1024px, 1280px, and 1440px viewport widths, all six
  routes render without unintended page-level horizontal scrolling.
- At compact widths, the sidebar is hidden by default and can be opened and
  closed through an accessible toggle, overlay click, and Escape.
- At expanded widths, the persistent sidebar remains available and does not
  reduce the content area below a usable width.
- `/stores` cards, selectors, notes, and action buttons are visible and usable
  without clipping.
- `/inbox` supports selecting a conversation, reading messages, switching mode,
  editing a draft, and sending a reply in the compact layout.
- `/queue` supports selecting a request and reaching its existing production,
  review, upload, CTA, nudge, and publish actions at every target width.
- Keyboard focus is visible, drawer controls are reachable, and no new
  accessibility violations are introduced. Playwright runs an axe scan at each
  route and width; new serious or critical violations block the change, while
  pre-existing lower-severity findings are tracked separately.
- Existing Admin unit and end-to-end tests remain green.

Minimum interaction thresholds: primary controls are at least 44px tall on
Compact widths; readable text does not rely on truncation for store names,
status, or action labels; only the Queue board may scroll horizontally, never
the page root. The drawer must expose an accessible label, `aria-expanded`, and
`aria-controls`, trap focus while open, and restore focus on close.

The Queue board must be wrapped in a named scroll region whose element owns the
overflow. Tests assert the page root has `scrollWidth === clientWidth` while the
Queue region may have `scrollWidth > clientWidth` at Compact and Medium widths.

## Engineering Review Decisions

- Full scope is approved: the shell and all six Admin routes ship together.
- CSS owns responsive layout decisions. React owns only drawer open/close state;
  `matchMedia` may be used solely to close stale drawer state after a mode
  transition, not as the layout source of truth.
- Use a native `<dialog>` for the Compact/Medium drawer, with explicit focus
  restoration, overlay close, Escape close, route-change close, and an
  accessible name.
- Share the navigation content through an `OpsNav` component while keeping the
  desktop aside and mobile dialog containers separate.
- Add a shared overflow contract: `.ops-main` and relevant grid/flex children
  use `min-width: 0`; only the Queue board owns horizontal overflow; long
  operator text may wrap with `overflow-wrap: anywhere`.
- Keep responsive CSS in the existing global stylesheet under a named section;
  do not migrate Admin to CSS Modules or rewrite existing Tailwind utilities.
- Add four named Playwright viewport projects: `compact-390`, `compact-768`,
  `medium-1024`, and `expanded-1280`. The six acceptance widths remain the
  manual/preview QA matrix.
- Add deterministic seeded states for every route and a visual baseline policy.
  Baselines live under `tests/e2e-cross/screenshots/<project>/<route>/<state>.png`;
  dynamic values are masked and baseline updates require UI-owner approval.
- Add `@axe-core/playwright`; serious and critical findings block the
  responsive accessibility suite. Lower-severity pre-existing findings are
  tracked separately.
- Define Inbox as list-or-detail on Compact and as a two-pane layout only when
  both panes remain at least 320px wide. Define Queue as a named local scroll
  region with 240px minimum columns and stacked detail below the board on
  Compact/Medium.
- Run responsive visual/a11y checks as a separately selectable suite. Keep the
  existing functional E2E suite unchanged and do not add API polling or fetches
  for layout behavior.

## Responsive Flow

```text
viewport width
      |
      v
CSS media queries ----> shell layout (aside visible/hidden)
      |                         |
      |                         +--> route layout contract
      |                              stores/cards, inbox panes,
      |                              queue local scroll, stacked forms
      v
menu toggle --> dialog open --> focus contained
                    |              |
          overlay / Escape / route change
                    v              |
             dialog close <--------+
                    |
                    v
             focus restored to toggle
```

## Failure Modes and Mitigations

- Page root regains horizontal overflow: assert root `scrollWidth ===
clientWidth`; keep overflow on the Queue region only.
- Drawer remains open after a route or breakpoint transition: close on link
  activation, pathname change, and expanded-mode transition.
- Focus escapes the modal or is lost after close: use native dialog behavior,
  explicit focus restoration, keyboard tests, and axe scans.
- Visual screenshots pass with empty data: run the canonical seeded state matrix
  before taking snapshots.
- Dynamic timestamps, IDs, or polling cause screenshot churn: mask dynamic
  regions and keep responsive suite data deterministic.
- A long URL or label widens a grid child: apply `min-width: 0` and
  `overflow-wrap: anywhere` at the shared layout boundary.
- Queue cards become unusable on narrow screens: enforce 240px column minimum,
  named local scroll ownership, and keyboard scroll assertions.

## Worktree and Parallelization Strategy

Implementation can be split into two independent workstreams after the shell
contract is agreed:

1. Shell/CSS work: `OpsShell`, `OpsNav`, drawer lifecycle, global responsive
   primitives, and route layout rules.
2. Verification work: deterministic fixtures, Playwright viewport projects,
   screenshot baselines, and axe integration.

The route markup changes depend on the shell/CSS contract, so they remain in the
shell workstream and are done sequentially with it. Verification can be
prepared in parallel once fixture entry points are identified, then run after
the layout work lands. If only one worktree is available, execute the two
workstreams sequentially in the order above.
