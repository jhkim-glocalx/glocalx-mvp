## Problem Statement

실사용자 출시가 임박했는데, 셀프서브 온보딩은 Google 로그인 직후에 자주 멈추고, 실제로 작동하는 GTM은 창업자가 방문해서 크롬으로 GBP를 직접 만들어주는 콘시어지다. 이 콘시어지 방식을 어드민 대시보드가 도구로 받쳐주지 못한다 — 창업자가 만든 리스팅을 사장님 계정에 연결할 수 없고, 운영자가 채팅에서 사장님 대신 GBP 셋업을 진행할 수도 없다.

## Demand Evidence

- 창업자가 실제 고객을 방문해 크롬으로 GBP를 만들어주고 사장님 로그인을 시키는 일이 **이미 일어나고 있음** (가설이 아니라 현재 영업 방식).
- 프로덕션에서 실제 GBP 리스팅이 엔드투엔드로 생성됨 (2026-08-11, "글로컬엑스/부산 서면로 39").
- 셀프서브 사장님은 Google 로그인 직후 이탈 — 관찰된 실패 패턴.

## Status Quo (워크어라운드와 그 비용)

창업자의 몸이 워크어라운드다: 방문 → 크롬에서 수동 GBP 생성 → 사장님 로그인 유도. 비용: (1) 창업자 시간이 온보딩당 소모, (2) 만들어준 리스팅과 앱 계정이 **연결되지 않아** 이후 발행·성과 기능이 그 가게에서 작동하지 않음, (3) 운영자가 채팅으로 안내는 할 수 있지만 실행은 못 함.

## Target User & Narrowest Wedge

- **핵심 사용자(당분간): 운영자(창업자 본인)** — Codex 콜드 리드와 합의된 진단: "고객이 원하는 것은 더 좋은 온보딩 UI가 아니라 설정을 완료해 주는 서비스."
- **웨지: 콘시어지 도구 완성** = ① 어드민에서 조직 계정이 관리하는 GBP 리스팅을 조회해 사장님 가게에 연결(입양/adoption) ② Inbox 채팅에서 운영자가 사장님 대신 GBP 셋업 액션 실행.

## Constraints

- **6시간 뒤 데모** (2026-08-24) — 데모 스코프는 Approach A로 고정. **[변경 2026-08-24 02시경]** 시연자는 CEO이고 환경은 **프로덕션(Vercel)** — 로컬 스텁 시연이 아니라 `glocalx-admin.vercel.app` + 실제 owner 앱으로 진행. 상세는 "프로덕션 데모 준비 체크리스트" 참조.
- 출시 버전(B)은 데모 직후 착수, 주 단위 내 완결 목표.
- Meta App Review(#41)는 외부 의존 — 출시 웨지에서 제외.
- 프로덕션은 이미 live 통합(GBP/Naver/OpenAI) — 스텁 아님. 실수하면 실고객 데이터에 닿는다.

## Premises (합의됨, D2)

1. 출시 웨지 = 콘시어지 도구 완성. 이미지 개선·다국어 캡션(#46)은 출시 후 트랙.
2. **IG 발행은 per-store 토큰 없으면 명시적 차단(BLOCKED)** — 현재 [post-flow.ts:93](../../apps/owner-app/src/posts/post-flow.ts)의 Instagram `createPost`는 토큰 미전달 시 글로벌 env 토큰(우리 테스트 계정)으로 fallback한다. 사장님 글이 남의 계정으로 나가는 신뢰 파괴 버그 표면이므로, per-store 배선(#39) 완결 전까지는 차단이 기본값.
3. DB는 출시 전에 건드리지 않는다 — 여기서 "건드리지 않는다"는 **dual-db 구조(SQLite/Postgres 병행) 자체를 통일하지 않는다**는 뜻이며, 순서 있는 마이그레이션 추가는 지금처럼 허용된다. `e2e:postgres` 게이트 유지. **트립와이어: 출시 전 dual-db 기인 버그가 1건이라도 추가 발생하면 즉시 로컬 Postgres 통일을 최우선 트랙으로 승격.** (창업자 결정, D4: "통일 없이 먼저 마무리해서 출시 버전 하나 만들고, 그 다음 통일해서 버전 또 만들자" — 출시 버전 뒤에 DB 통일 버전이 예정된 트랙으로 명문화됨.)
4. 미커밋 org-locations 작업(≈310줄: `packages/integrations/src/gbp-org-locations.ts`, 어드민 stores 콘솔 CONFIRM_ADOPTION/REJECT_ADOPTION, org-locations API 라우트)을 main 위로 회수(절차는 A-1)하는 것이 1순위. 현재 머지된 브랜치(PR #60) 위에 커밋 없이 방치 — 유실 위험.
5. 채팅 GBP 셋업은 기존 점주용 GBP 셋업 도메인 서비스(`apps/owner-app/src/gbp/setup.ts`)를 어드민 권한 경계로 감싸 재사용. 셋업 로직을 어드민용으로 복제하지 않는다.

## Cross-Model Perspective (Codex 콜드 리드, 2026-08-24)

1. **Steelman**: GlocalX의 강한 형태는 "AI 마케팅 SaaS"가 아니라, 디지털 운영이 어려운 자영업자를 대신해 GBP 개설·연결·콘텐츠 발행까지 수행하는 **인간 개입형 로컬 비즈니스 운영체제**. 자동화는 원가를 낮추고, 관리자는 실패한 흐름을 이어받아 결과를 끝까지 보장한다.
2. **핵심 통찰**: "셀프서브 고객은 Google 로그인 직후 멈추지만, 창업자가 직접 방문해 설정하면 실제 GBP 개설까지 된다" → 고객이 원하는 것은 온보딩 UI가 아니라 **설정을 완료해 주는 서비스**. 당분간 제품의 핵심 사용자는 점주가 아니라 운영자.
3. **반박된 전제**: P3(출시 전 DB 통일 안 함). Codex: "실결제 고객 데이터를 다루는 시점엔 통일이 결국 싸다; dual-db 사고가 한 번 더 나면 그것이 증거." → 트립와이어 명문화로 수용(전제 3), 창업자가 출시 후 통일 버전을 로드맵에 확정하는 것으로 종결.
4. **48시간 프로토타입 제안**: 관리자 주도 GBP 완료 경로 하나 — 매장 화면(조직 GBP 목록→선택→연결/거절), 채팅 "GBP 설정 시작" 액션 카드, admin API 4개(adoption-candidates / adoption / adoption/reject / setup/actions), 마지막 것은 관리자 권한+감사 로그를 붙여 기존 도메인 서비스 호출. 멱등성·상태 전이 검증·운영자/시각/외부 GBP ID 기록 포함. IG는 매장 토큰 없으면 명시적 발행 차단.

## Approaches Considered

### Approach A: 데모 우선 — 입양(adoption) 경로만 완결 (Effort S, Risk Low)

미커밋 org-locations 작업을 main 위로 회수해 완성: 어드민 stores 콘솔에서 조직 리스팅 조회 → 선택 → 사장님 가게에 연결/거절. + IG 글로벌 토큰 fallback 차단 가드. 채팅 셋업은 제외. 6시간 내 데모 가능한 유일한 안.

### Approach B: 출시 버전 — 채팅 GBP 셋업 포함 (Effort M, Risk Med)

A + Inbox "GBP 설정 시작" 액션 카드 + `POST /api/admin/stores/:storeId/gbp/setup/actions` (어드민 권한 + 감사 로그 + 멱등성, 기존 셋업 도메인 서비스 호출). 리스크는 어드민이 owner-store 소유권 경계를 넘는 새 권한 경로 — 서두르면 보안 구멍.

### Approach C: 운영자 콕핏 — 스텝별 수동 대체 패널 (Effort L) — 백로그

온보딩~발행 전 스텝의 상태를 가게별로 보여주고 스텝마다 "대신 실행" 버튼. "모든 자동화에 수동 대체"의 일반해지만 현재 규모(수십 가게)엔 과설계. 셀프서브 이탈 지점 계측이 부산물로 나오므로 고객 수가 운영자 손을 넘칠 때 재개.

## Recommended Approach (확정, D5)

**A → B 순차.** 데모(6h)는 A, 출시 버전은 B(A는 B의 부분집합), C는 백로그. B 다음 트랙으로 **DB 통일 버전**(로컬 dev를 Docker Postgres로, SQLite/`ensure*` 이중 유지보수 청산) 확정.

실행 순서:

1. **[A-1]** 미커밋 작업 회수 — 정확한 절차: 현재 작업 트리는 커밋되지 않았으므로 rebase가 아니라 `git switch -c feat/gbp-org-locations origin/main` (미커밋 변경은 새 브랜치로 그대로 따라옴) → 커밋 → PR. 유실 위험 제거가 데모 준비의 첫 스텝. 잡파일 `glocalx-post.png.jpg`는 커밋에서 제외.
2. **[A-2]** adoption 경로 완결: org-locations 조회 → 콘솔 picker → `CONFIRM_ADOPTION`/`REJECT_ADOPTION` (미커밋 작업이 기존 `transitionGbpAccess` 상태 머신을 확장하는 액션들) → `gbp_access_requests` 상태 전이 + 감사 로그.
   - 엣지 케이스 기대 동작: **이미 다른 가게에 입양된 리스팅** → picker에서 표시하되 선택 시 거부(UI만이 아니라 서버 측 검증 포함); **이미 GBP location이 있는 가게** → adoption 진입 차단; **org-locations API 실패/빈 목록** → 콘솔에 실패 사유 표시(무한 스피너 금지); **잘못된 입양 취소** → 기존 override 셀렉터가 탈출구(전용 undo는 B에서 판단).
3. **[A-3]** IG 발행 가드 (데모가 길어지면 데모 직후 별도 소형 PR로 분리 가능): 레이어를 명시하면 — `post-flow.ts`가 `store_channel_links`에서 per-store 토큰을 읽어 어댑터에 전달; 토큰 부재 시 **어댑터 호출 전에** `INSTAGRAM_PUBLISH_NOT_CONFIGURED` BLOCKED 반환; Instagram 어댑터 내부의 글로벌 env 토큰 fallback 경로 삭제.
4. **[B-0]** 셋업 서비스 호스팅 결정 (Open Q1과 함께 `/plan-eng-review`에서): `gbp/setup.ts`는 `apps/owner-app/src`에 있고 앱 간 코드 공유는 `packages/*` 경유가 이 레포의 규칙. 선택지 = ① 셋업 도메인 서비스를 패키지로 추출, ② 엔드포인트를 owner-app의 기존 `api/admin/` 경로에 호스팅(선례 있음). 이 결정 없이는 B-1 착수 불가.
5. **[B-1]** admin setup-actions 엔드포인트 (라우트 형태는 B-0/Q1 결과에 따르는 스트로맨: `POST .../stores/:storeId/gbp/setup/actions`): 어드민 세션 검증 → 대상 store 명시 → 기존 셋업 도메인 서비스 호출 → `audit_logs` 기록(운영자 id, 시각, 액션, 외부 GBP id) + 멱등성 키(구체 구성은 eng review에서 확정).
6. **[B-2]** Inbox 액션 카드: 핸드오프된 대화에서 "GBP 설정 시작" → 현재 단계·실패 사유 표시 → "관리자가 계속하기". **카드에 노출할 액션 목록은 Assignment의 현장 기록으로 확정** — 여기 적힌 구성은 잠정안.
7. **[B-3]** 프로덕션형 검증: 실제 Google 테스트 계정으로 "후보 조회 → 채택 → 연결 상태 확인" 한 경로 엔드투엔드 — **환경은 Vercel 프리뷰(또는 전용 테스트 가게)**로 한정하고, 채택/거절에 쓸 안전한 리스팅(예: 우리 조직의 테스트 리스팅)을 사전 지정. 프로덕션 실고객 리스팅으로는 검증하지 않는다.

## Open Questions

1. **어드민 권한 경계의 형태 + 셋업 서비스 호스팅(B-0)**: setup-actions가 owner 세션 없이 store를 조작하는 첫 경로. 별도 admin-scoped 서비스 래퍼로 갈지, 도메인 서비스에 actor(owner|operator) 개념을 넣을지, 코드를 패키지로 추출할지 owner-app `api/admin/`에 호스팅할지 — B 착수 전 `/plan-eng-review`에서 결정. B-1의 라우트 형태는 그 결정 전까지 스트로맨.
2. **입양된 리스팅의 verification 상태 처리**: 창업자가 만든 리스팅이 미인증(needs-verification)일 때 발행 차단 로직(#45)과의 상호작용 — 입양 시 운영자에게 어떤 상태로 보여줄지.
3. Meta App Review(#41) 신청 시점 — B와 병행 가능한 외부 트랙, 언제 넣을지.
4. DB 통일 버전의 구체 범위: 로컬 dev만 Postgres로 갈지, SQLite 경로(e2e 속도 이점)를 완전히 제거할지.

## 리허설 결과 (2026-08-24 새벽, 프로덕션 실측)

P-4 리허설을 프로덕션에서 완료. 통과: 운영자 로그인 → override→`adoption_review` 전이 → **picker에 실제 org 리스팅 5건 로드**(글로컬엑스 서울/노티스/우빈떡볶이/고기그릴/Acabar — env·모드·어댑터 전 구간 검증) → location 보유 가게 재입양 시 서버 409 거부(location 덮어쓰기 방어 성공) → override로 원상복구(undo 경로 검증). 리허설이 잡아낸 결함 3건:
